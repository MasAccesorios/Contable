# Roadmap de Desarrollo — MAS Accesorios (App Contable)

**Arquitectura confirmada:** SPA en JavaScript vanilla (sin framework), Bootstrap 5,
persistencia local IndexedDB + sincronización con Firebase Realtime Database.
Sin backend propio (no Laravel/MySQL — ese stack solo queda como referencia
de reglas de negocio en `Esp. Tecnicas Contable.md`).

**Estado actual:** desarrollo local en `D:\Contable`, pruebas offline,
Firebase se conecta cuando el software esté terminado.

---

Objetivo: dejar de perder tiempo en parches y tener una base estable.

- [ ] Inicializar Git real en `D:\Contable` (`git init`), aunque sea repo local o

- [ ] Renombrar `Esp. Tecnicas Contable.md` → `Reglas_de_Negocio.md` y quitar

      y 3 (usuarios con bcrypt/roles vía backend). Las reglas de negocio
      (secciones 6, 7, 8, 9, 16) siguen siendo válidas y son tu mejor

- [ ] Actualizar `README.md` para que sea la única fuente de verdad de

## Fase 1 — Saneamiento de datos (antes de tocar más código)

Objetivo: que los datos que vas a usar para probar no arrastren errores del
histórico de Alegra.

- [ ] Investigar el origen del stock negativo masivo (133 productos, el peor
      caso en -48,066 unidades). Hipótesis más probable: ventas o
      devoluciones importadas más de una vez durante pruebas de sync.
      Antes de decidir cómo corregirlo, corre un conteo de cuántas veces
      aparece cada `alegra_invoice_id` en tus datos de facturas — si hay
      duplicados ahí, es la causa.
- [ ] Definir una política clara: ¿el stock en la app propia se **recalcula
      siempre desde Alegra** (Alegra como maestro, tal como dice tu propia
      sección 16.9) o se **ajusta manualmente**? Con Alegra como maestro,
      lo más seguro es que cada sync haga un *reset* del stock a lo que
      diga Alegra, no un incremento/decremento acumulado.
- [ ] Decidir qué hacer con el campo `ubicacion` (100% vacío hoy): o lo
      llenas en un ajuste manual único, o lo quitas del modelo si no lo vas
      a usar — un campo vacío en 1,887 registros no aporta nada y confunde.
- [ ] Escribir un script simple de validación (`validar_datos.py`) que corras
      **cada vez** que importes desde Alegra: SKU no vacío, stock ≥ 0 (o
      alerta si es negativo), precio venta ≥ costo. Así detectas el próximo
      error de sync en segundos, no por auditoría manual.

## Fase 2 — Estructura modular del frontend (la base para todo lo demás)

Aquí es donde aplica el criterio de "funciones globales compartidas" que ya
tenías en mente (Ver / Editar / Anular / Imprimir / Pagar) — es la idea
correcta, solo hay que ordenarla:

```
/js
  /core
    app.js          -> enrutador SPA, arranque, estado global
    auth.js         -> sesión / roles
    db.js           -> capa única de acceso a datos (IndexedDB + Firebase)
  /shared
    crud.js         -> funciones genéricas: Ver, Editar, Anular, Imprimir, Pagar
    ui.js           -> toasts, modales, componentes repetidos
    validaciones.js -> reglas comunes (montos, fechas, campos requeridos)
  /modules
    /clientes
    /productos
    /ventas
    /cartera
    /bancos
    /gastos
    /reportes
    /integracion-alegra
```

Regla de oro: **ningún módulo llama directamente a Firebase**. Todos pasan
por `core/db.js`. Así, si el día de mañana cambias de Firebase a otra base
de datos, solo tocas un archivo, no 20.

- [ ] Mover la lógica de `handleGlobalSearch` y `navigateTo`/`navigateBack`
      (la que ya armaste en `merge_app.py`) a `core/app.js` como base limpia,
      sin parches encima.
- [ ] Crear `shared/crud.js` con las 5 funciones genéricas y que cada módulo
      solo las invoque pasando su configuración (nombre de colección, campos,
      permisos).

## Fase 3 — Reglas de negocio por módulo (usando tu propio documento)

Ir módulo por módulo, en este orden de prioridad (por dependencia real):

1. **Productos / Inventario** — ya tienes los datos, hay que llegar a
   stock confiable (depende de Fase 1).
2. **Clientes** — más simple, poca lógica.
3. **Ventas** (contado/crédito) — depende de productos y clientes.
4. **Cartera** — depende de ventas a crédito.
5. **Bancos y movimientos** — depende de ventas de contado y de cartera.
6. **Gastos** — depende de bancos.
7. **Dashboard** — depende de que todo lo anterior ya sume bien.
8. **Integración Alegra** (sección 16 del doc) — al final, cuando el modelo
   de datos propio ya esté estable, para no sincronizar contra un blanco
   en movimiento.

## Fase 4 — Conexión real con Firebase (cuando termines pruebas locales)

- [ ] Revisar reglas de Firebase (`auth != null` ya está bien como mínimo,
      pero conviene reglas por rol, no solo por sesión).
- [ ] Quitar el patrón `?auth=TOKEN` en URL que menciona tu propio README —
      usar headers de autenticación, no query string.
- [ ] Definir estrategia de conflicto IndexedDB ↔ Firebase: ¿quién gana si
      hay cambios offline y luego se reconecta? (recomendado: Firebase como
      maestro, IndexedDB solo como caché de lectura offline).
